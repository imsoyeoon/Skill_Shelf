# Skill Shelf — 제품 요구사항 문서(PRD)

> 버전: 0.1 / 작성일: 2026-11-24 / 상태: 팀 검토용 초안  
> 용도: 수업 과제 제출, 팀의 MVP 범위 합의, 원프롬프트 개발 시 AI가 참조할 제품 요구사항  
> 작성 근거: `23_PRD_TechSpec.pdf`, `Skill_Shelf_Preview.html`, 팀 프로젝트에 관한 대화

## 문서 적용 기준

- 이 문서는 사용자가 무엇을 할 수 있어야 하고, 왜 필요한지, 무엇으로 완료를 판단하는지 정의한다.
- 수업 자료의 8개 PRD 구성 요소와 생성AI 앱의 추가 요구사항을 반영한다. 구현·배포 형태는 수업 자료의 Streamlit 앱 기준을 따른다.
- 화면 구성과 기능은 제공된 HTML 시안을 기준으로 한다. 모델, 프롬프트 전문, 데이터 구조, 함수/API, 라이브러리 및 비용 설계는 별도 Tech Spec에서 정한다.
- **확인된 내용:** 프로젝트 맞춤 스킬·에이전트 추천이라는 팀의 목적, Skill Shelf라는 시안 이름, 시안에 있는 탐색·검색·분류·추천·파일 첨부·상세 보기·GitHub 갱신 화면.
- **초안에서 제안한 내용:** 추천 대상 범위를 SKILL.md 기반 스킬로 우선 제한하는 것, 등록 저장소 중심 갱신, 파일 분석 안전 한도, 응답 시간 및 성공 지표. 문서 끝의 팀 확인 사항과 함께 검토한다.
- **구현 상태:** 제공된 HTML은 단독 실행용 미리보기다. 단독 모드의 추천은 키워드와 예시 목록을 사용하고, 첨부파일은 이름만 추천에 활용한다. 실제 AI 호출, 파일 내용 분석, GitHub 갱신을 수행하는 백엔드와 배포 앱은 제공 자료에서 확인되지 않았다. 아래 요구사항은 구현 완료 보고가 아니다.

## 1. 개요(Overview)

### 1.1 제품 소개

Skill Shelf는 AI의 도움을 받아 프로그램을 만드는 사용자가 자신의 프로젝트에 필요한 에이전트 스킬을 찾도록 돕는 웹 애플리케이션이다. 사용자가 프로젝트 목표·기술·막힌 부분을 설명하거나 프로젝트 파일을 첨부하면, 등록된 스킬 중 관련성이 높은 후보와 추천 이유를 제공한다. 사용자는 스킬 목록을 직접 탐색하거나 원문을 열어 적용 가능성을 확인할 수 있다.

**핵심 가치 제안:** “내가 만드는 프로젝트를 설명하면, 지금 필요한 스킬과 그 이유·원문 링크를 한곳에서 확인한다.”

### 1.2 해결하려는 문제

다음은 팀의 문제 가설이며, 사용자 테스트로 확인한다.

1. 스킬 정보가 여러 저장소에 흩어져 있어 찾고 비교하는 데 시간이 든다.
2. 이름과 소개만으로 자신의 프로젝트에 적합한지 판단하기 어렵다.
3. 초보 사용자는 어떤 기능이나 개발 단계에 도움이 필요한지 검색어로 표현하기 어렵다.
4. 추천 결과의 출처와 실제 사용 조건을 확인할 수 있어야 선택에 도움이 된다.

### 1.3 MVP의 핵심 흐름

사용자가 프로젝트 설명 또는 유효한 프로젝트 파일을 제공한다. 서비스는 사용 가능한 후보 중 관련 스킬을 최대 3개 제시한다. 사용자는 각 추천의 이유를 읽고 상세 화면에서 SKILL.md나 저장소를 연다.

직접 찾아보고 싶은 사용자는 카테고리와 검색어로 목록을 좁혀 같은 상세 화면으로 진입한다.

### 1.4 용어와 추천 대상

| 용어 | 이 문서에서의 뜻 |
| --- | --- |
| 바이브 코더 | 자연어로 AI에게 요구사항을 전달하며 프로그램을 만드는 사용자 |
| 스킬 | 특정 작업을 수행하도록 AI 코딩 도구에 제공하는 작업 지침·자료 묶음 |
| 추천 후보 | 서비스에 등록되어 식별 정보와 출처를 확인할 수 있는 스킬 |
| 원문 | 스킬의 실제 SKILL.md 및 그 파일이 포함된 GitHub 저장소 |
| MVP | 입력부터 추천·원문 확인까지 핵심 경험이 실제로 동작하는 첫 번째 제품 |

초기 MVP의 추천 단위는 **SKILL.md가 있는 에이전트 스킬**로 제안한다. 독립 실행 에이전트까지 추천하려면 종류·사용 환경·상세 정보에 대한 요구사항을 추가해야 한다. 이 범위는 팀에서 확정한다.

## 2. 목표(Goals)

| ID | 목표 | 목표가 달성된 상태 |
| --- | --- | --- |
| G-01 | 프로젝트에 필요한 스킬을 쉽게 찾게 한다. | 사용자가 설명이나 파일을 제출하고 관련 후보와 이유를 확인한다. |
| G-02 | 추천을 판단할 근거를 제공한다. | 추천마다 프로젝트와의 관련성, 기능 설명, 원문 링크가 있다. |
| G-03 | 흩어진 정보를 한 화면에서 탐색하게 한다. | 카테고리·검색·상세 보기를 통해 원하는 스킬을 찾는다. |
| G-04 | 추천 방식과 데이터 상태를 명확하게 알린다. | 실제 AI 추천, 키워드 추천, 미리보기 데이터를 구분한다. |
| G-05 | 수업에서 시연 가능한 MVP를 완성한다. | Streamlit 앱에서 실제 AI 추천 정상 시나리오와 오류 시나리오를 검증한다. |

성공 수치와 측정 방법은 7절에서 정의한다. 이 문서에 기재한 수치는 구현 후 확인할 목표이며 측정 결과가 아니다.

## 3. 대상 사용자(Target Users)

### 3.1 주요 사용자

- **AI 코딩 입문자:** 프로젝트 아이디어는 있으나 어떤 스킬을 활용할지 모르는 사람.
- **학생·소규모 프로젝트 개발자:** 제한된 시간에 디자인, 코드 개선, 디버깅, 문서 처리 등을 해결하려는 사람.
- **진행 중인 프로젝트가 있는 사용자:** 코드나 설정 파일을 바탕으로 현재 필요한 도움을 찾으려는 사람.

### 3.2 대표 사용 상황

- React 기반 대시보드의 화면 성능을 개선하고 싶다.
- 랜딩 페이지의 디자인을 다듬고 브라우저 동작을 확인하고 싶다.
- Python으로 엑셀 보고서를 만들고 PDF로 내보내고 싶다.
- 오류를 재현하고 원인을 분석하는 작업에 도움을 받고 싶다.

이 예시는 사용자가 수행하려는 작업을 설명한다. 특정 후보의 실제 기능과 호환성은 등록 시 원문으로 확인해야 한다.

## 4. 사용자 스토리(User Stories)

각 스토리에 완료 여부를 판단할 인수 조건을 붙인다.

| ID | 사용자 스토리 | 인수 조건 |
| --- | --- | --- |
| US-01 | 스킬을 찾는 사용자로서, 나는 목록을 검색하고 분류하고 싶다. 내 작업과 관련된 후보를 빠르게 찾기 위해서다. | 검색어와 카테고리가 함께 적용되고, 결과 수가 일치하며, 결과가 없으면 안내한다. |
| US-02 | AI 코딩 입문자로서, 나는 프로젝트를 자연어로 설명하고 추천받고 싶다. 적절한 검색어를 몰라도 도움을 받기 위해서다. | 유효한 설명을 제출하면 최대 3개 후보와 프로젝트에 연결된 이유를 표시한다. |
| US-03 | 진행 중인 프로젝트가 있는 사용자로서, 나는 파일을 첨부하고 싶다. 프로젝트 내용을 매번 설명하는 부담을 줄이기 위해서다. | 허용 범위의 파일 내용을 분석에 반영하며, 읽지 못한 파일을 읽었다고 표시하지 않는다. |
| US-04 | 추천을 받은 사용자로서, 나는 추천 이유와 출처를 확인하고 싶다. 적용할 가치가 있는지 판단하기 위해서다. | 추천 결과와 목록에서 상세 화면을 열 수 있고, 확인된 원문·저장소 링크가 제공된다. |
| US-05 | 스킬을 탐색하는 사용자로서, 나는 GitHub 정보를 갱신하고 싶다. 현재 후보와 저장소 정보를 확인하기 위해서다. | 갱신 결과와 확인 시점을 표시하고, 실패 시 기존 목록을 유지하며 실패 사실을 알린다. |
| US-06 | 처음 방문한 사용자로서, 나는 입력 예시를 선택하고 싶다. 어떤 설명을 써야 하는지 이해하기 위해서다. | 예시 버튼을 누르면 입력창에 해당 문장이 채워지고, 수정 후 직접 제출할 수 있다. |
| US-07 | 추천을 요청한 사용자로서, 나는 처리 상태와 실패 이유를 알고 싶다. 기다리거나 입력을 수정하거나 재시도하기 위해서다. | 처리 중임을 표시하고 중복 요청을 막으며, 빈 입력·근거 부족·서비스 실패를 구분해 안내한다. |

## 5. 기능 요구사항(Functional Requirements)

### 5.1 우선순위와 출시 기준

- **P0 / 필수:** MVP 핵심 가치를 구성하는 기능. 모든 P0 인수 조건을 통과해야 MVP 완료로 판단한다.
- **P1 / 개선:** 핵심 흐름을 검증한 뒤 추가할 기능.
- 현재 HTML에 보이는 기능을 유지하는 방향으로 아래 항목을 P0으로 정리했다. 기간상 범위를 줄일 경우, 팀이 PRD와 시안을 함께 변경한다.

### 5.2 FR-001 — 스킬 목록 표시 [P0]

**요구사항**

- 등록된 스킬을 카드로 표시한다.
- 카드에는 이름, 한국어 기능 설명, 카테고리, 저장소 이름, 저장소 별 수를 표시한다.
- 별 수는 개별 스킬의 지표가 아닌 **저장소 전체의 수치**임을 표시한다.
- 예시 데이터와 실제 조회 데이터의 출처를 구분한다.
- 등록 정보가 없거나 일부 항목을 읽지 못한 경우 안내하고, 사용 가능한 나머지 항목은 표시한다.

**인수 조건**

1. 유효한 후보가 있으면 이름·설명·분류·저장소 정보가 있는 카드가 나온다.
2. 같은 저장소·파일 경로의 항목이 중복 표시되지 않는다.
3. HTML의 예시 별 수를 실제 최신 값으로 표시하지 않는다.
4. 실제 별 수를 확인할 수 없으면 미확인 상태로 표시한다.

### 5.3 FR-002 — 카테고리·검색·더 보기 [P0]

**요구사항**

- 카테고리는 전체, 프론트엔드, 디자인, 백엔드, 테스트·디버깅, 개발 워크플로, 문서·데이터, 기타로 구성한다.
- 검색은 이름·설명·저장소 이름·카테고리명을 대상으로 대소문자를 구분하지 않고 수행한다.
- 검색어와 카테고리는 동시에 적용한다.
- 초기 최대 6개를 표시하며 ‘더 보기’를 누르면 최대 12개씩 추가 표시한다.
- 검색어 또는 카테고리를 변경하면 표시 개수를 초기 상태로 되돌린다.

**인수 조건**

1. 표시 개수와 전체 검색 결과 수를 혼동하지 않고, 검색 결과 수를 정확히 안내한다.
2. 남은 항목이 있을 때만 ‘더 보기’가 보인다.
3. 검색 결과가 없으면 ‘조건에 맞는 스킬이 없습니다’를 표시한다.
4. 백엔드 등 특정 카테고리에 등록 후보가 없더라도 오류 없이 빈 결과를 보여준다.

### 5.4 FR-003 — 스킬 상세·원문 이동 [P0]

**요구사항**

- 목록 카드나 추천 결과를 선택하면 같은 스킬의 상세 화면을 연다.
- 상세에는 이름·기능 설명·분류·저장소·파일 경로와 원문 링크를 제공한다.
- ‘SKILL.md 보기’와 ‘저장소 열기’로 실제 출처를 확인할 수 있게 한다.
- 사용할 수 있는 환경이나 사용 조건이 확인된 경우 함께 표시하고, 확인되지 않은 호환성을 보장하지 않는다.
- 사용자는 닫기 버튼 또는 키보드로 상세 화면을 닫을 수 있다.

**인수 조건**

1. 선택한 스킬과 상세 내용·링크가 일치한다.
2. 원문 링크가 확인된 저장소·브랜치·경로를 가리킨다.
3. 원문 주소를 확인하지 못했다면 링크를 만들어 내지 않고 미확인 상태를 표시한다.
4. 이 화면에서 사용자 프로젝트에 스킬을 설치하거나 코드를 실행하지 않는다.

### 5.5 FR-004 — 프로젝트 설명 입력·예시 선택 [P0]

**요구사항**

- 사용자가 목표, 사용 기술, 필요한 도움을 자유롭게 작성할 수 있다.
- 설명은 최대 6,000자로 제한한다.
- 텍스트와 파일을 함께 제출하거나, 둘 중 하나만 제출할 수 있다.
- 빈 설명과 첨부파일이 없는 상태에서는 제출하지 않고 안내한다.
- 시안의 예시 3개를 유지한다: Next.js 대시보드, 랜딩 페이지 제작, Python 리포트 자동화.
- Enter로 제출하고 Shift+Enter로 줄바꿈한다. 한글 조합 중 Enter는 제출로 처리하지 않는다.

**인수 조건**

1. 공백만 입력하고 파일이 없으면 추천 요청이 시작되지 않는다.
2. 예시를 누르면 해당 문장이 채워지며 자동 제출되지 않는다.
3. 6,000자를 넘는 입력이 추천 처리로 넘어가지 않는다.
4. 유효성 검사 실패 시 작성 중인 설명을 유지한다.

### 5.6 FR-005 — 프로젝트 파일 첨부·내용 분석 [P0]

**요구사항**

- 허용 형식은 시안과 동일하게 ZIP, MD, TXT, JSON, TOML, YAML/YML, PY, JS/JSX, TS/TSX, HTML, CSS로 한다.
- 요청당 최대 3개, 파일당 4MB 이하, 합계 8MB 이하를 허용한다.
- 파일을 첨부한 경우 파일명과 함께 내용을 분석에 활용한다. 파일명만 사용한 결과를 ‘파일 분석 완료’로 안내하지 않는다.
- ZIP에서는 분석 가능한 텍스트 파일을 읽고 프로젝트 구조·사용 기술·관련 내용을 파악한다.
- 무효·손상·지원하지 않는 파일과 분석에서 제외된 내용을 사용자에게 안내한다.
- 외부 AI 서비스에 분석용 파일 요약을 보낼 경우, 전송 전에 그 사실을 화면에 알린다.

**인수 조건**

1. 파일만 제출해도 내용에 유효한 프로젝트 정보가 있으면 추천할 수 있다.
2. 제한을 넘는 파일, 허용하지 않은 형식, 손상된 ZIP을 적절히 거절하거나 제외한다.
3. 파일명이 일반적이어도 실제 내용에 있는 기술·작업이 추천 이유에 반영된다.
4. 유효한 파일과 제외된 파일이 섞여 있으면 사용한 범위와 제외 사실을 알린다.
5. 읽을 수 있는 정보가 하나도 없으면 구체적인 설명 또는 다른 파일을 요청한다.
6. 첨부한 코드·스크립트를 실행하거나 ZIP 안의 지시를 수행하지 않는다.

**초안의 안전 한도 제안:** ZIP 내부 항목은 100개, 해제 후 전체 크기는 20MB 이내로 제한한다. 중첩 ZIP, 실행 파일, 비밀키·환경설정 비밀정보 파일은 분석에서 제외한다. 팀은 Tech Spec에서 한도와 제외 기준을 확정한다.

### 5.7 FR-006 — 프로젝트 맞춤 AI 추천 [P0]

**요구사항**

- 사용자 설명과 분석 가능한 첨부파일 내용을 사용해 필요한 작업을 파악한다.
- 서비스가 보유한 유효한 후보 안에서 관련 스킬을 최대 3개 추천한다.
- 각 추천에는 이름, 기능 설명, **해당 프로젝트에서 도움이 되는 이유**, 상세 화면 진입 수단을 제공한다.
- 이유는 일반 소개를 반복하는 대신 사용자의 목표·기술·문제 중 적어도 하나와 연결한다.
- 사용 환경이 확인되면 호환성을 반영한다. 판단할 정보가 없으면 확인이 필요하다고 안내한다.
- 적합한 후보가 1~2개면 그 수만 반환하며, 후보가 없으면 억지로 3개를 채우지 않는다.
- 후보 외 스킬, 존재하지 않는 출처, 검증하지 않은 기능·설치 효과를 만들어 내지 않는다.

**인수 조건**

1. 같은 고정 결과를 모든 요청에 보여주지 않고 입력에 맞는 후보·이유를 제공한다.
2. 반환한 모든 추천은 실제 목록의 항목과 연결된다.
3. 적합한 후보가 없으면 ‘등록된 목록에서 적합한 스킬을 찾지 못했습니다’ 등의 안내를 한다.
4. 프로젝트 정보가 부족하면 필요한 목표·기술·막힌 부분을 구체적으로 요청한다.
5. 실제 AI 호출에 성공한 정상 시나리오를 배포 앱에서 1건 이상 시연한다. 키워드 대체 동작은 이 조건을 대신하지 않는다.

### 5.8 FR-007 — AI·키워드·미리보기 모드 구분 [P0]

| 모드 | 사용 조건 | 사용자에게 보이는 상태 |
| --- | --- | --- |
| AI 추천 | 실제 AI 요청으로 후보를 선정하고 이유를 생성한 경우 | ‘AI 연결됨’ 및 AI로 생성한 결과라는 안내 |
| 키워드 추천 | AI를 사용할 수 없거나 요청 실패 후 등록 목록을 키워드로 추천한 경우 | ‘키워드 추천’ 및 전환 이유 |
| 시안·예시 추천 | 단독 미리보기에서 예시 목록을 이용한 경우 | ‘시안 · 예시 추천’, ‘미리보기 데이터’ |

**인수 조건**

1. AI 키가 없거나 실제 호출이 실패했는데 ‘AI 연결됨’으로 표시하지 않는다.
2. 결과를 만들 때 적용한 추천 방식을 사용자에게 알린다.
3. 키워드 추천에서도 관련 후보가 없으면 구체적인 입력을 요청한다.
4. 미리보기에서 파일명만 활용한다면 이 제한을 분명히 표시한다.

### 5.9 FR-008 — GitHub 목록 불러오기·갱신 [P0]

**요구사항**

- ‘GitHub에서 불러오기’를 누르면 대상 저장소의 스킬 정보와 저장소 별 수를 확인·갱신한다.
- ‘별 1만 개 이상’은 **저장소 단위**의 조건이며, 수집 시 확인한 값으로 판단한다.
- 최소한 실제 SKILL.md 존재 여부와 출처를 확인한 항목을 등록한다.
- 갱신한 목록에 출처와 최근 성공 확인 시점을 표시한다.
- 실패하면 기존에 확인된 목록을 유지하고 실패 이유를 이해할 수 있게 안내한다.
- 초기 데이터만 사용할 때는 미리보기 또는 초기 데이터임을 밝힌다.
- 별 수는 발견·정렬을 위한 참고 정보이며 품질·안전성·호환성을 보장하는 지표로 안내하지 않는다.

**인수 조건**

1. 성공 시 갱신된 결과 수와 확인 시점이 맞게 표시된다.
2. 네트워크 오류나 GitHub 요청 한도 등의 문제를 성공으로 표시하지 않는다.
3. 실패 때문에 기존 유효한 목록이 빈 목록으로 바뀌지 않는다.
4. 실제로 확인하지 못한 별 수나 현재 존재 여부를 확정해서 표시하지 않는다.

**수집 범위에 대한 초안 제안:** MVP에서는 팀이 등록한 대상 저장소를 갱신한다. GitHub 전체에서 모든 스킬 저장소를 자동 발견하는 기능은 이후 범위로 둔다. 대상 저장소 목록은 팀이 확인 후 확정한다.

### 5.10 FR-009 — 처리 상태·오류·현재 세션 [P0]

**요구사항**

- 추천·갱신 처리 중에는 진행 상태를 표시하고 중복 제출을 막는다.
- 정상·오류 응답이 끝나면 사용자가 다시 요청할 수 있다.
- 실패 시 재시도할 수 있게 설명과 파일 선택 상태를 가능한 범위에서 유지한다.
- 추천 대화와 결과는 현재 세션에서 확인할 수 있다.
- 예외 화면이나 내부 오류 원문 대신 사용자가 다음 행동을 알 수 있는 메시지를 표시한다.

**초안 가정:** 화면에는 현재 세션의 대화를 표시하되, 각 추천은 해당 요청의 설명과 파일을 기준으로 처리한다. 이전 대화를 자동으로 이어 해석하는 다중 턴 상담은 MVP 필수 기능으로 두지 않는다.

**인수 조건**

1. 제출 버튼을 반복 클릭해도 동일 요청이 중복 처리되지 않는다.
2. 빈 입력, 분석 가능한 정보 없음, 추천 후보 없음, 외부 서비스 실패를 구분한다.
3. 오류 후 재입력·재시도가 가능하고 화면이 계속 잠기지 않는다.
4. 실패한 요청을 정상 추천 응답처럼 표시하지 않는다.

특정 스킬의 기능·출처를 확인한 뒤 기대 후보를 확정한다. 평가가 끝난 뒤 성공 기준을 결과에 맞춰 바꾸지 않는다.

| Q-04 | 브라우저에서 버튼·페이지 이동 테스트 | 웹 테스트 후보와 사용자 동작 검증을 연결한다. |
| Q-05 | Python 기반 엑셀 보고서 자동화 | 스프레드시트·데이터 관련 후보를 제시한다. |
| Q-06 | 보고서를 PDF로 생성·내보내기 | PDF 처리 후보가 등록되어 있다면 제시한다. PDF 파일 업로드 지원과 혼동하지 않는다. |
| Q-07 | 구현 전에 요구사항과 작업 순서 정리 | 기획·작업 계획 후보와 구체적 목적을 연결한다. |
| Q-08 | 일반적인 이름의 MD/TXT 파일에 React 프로젝트 설명 포함 | 파일명보다 실제 내용을 반영해 추천하고 이유를 설명한다. |
| Q-09 | ‘아무거나 추천해줘’처럼 정보 부족 | 기술·목표·막힌 부분에 대한 보완 입력을 요청한다. |
| Q-10 | ‘오늘 학교 식단 알려줘’처럼 서비스와 무관 | 적합한 후보가 없음을 알리고 스킬 추천에 필요한 입력을 안내한다. |

품질 통과는 “후보가 관련 작업을 지원하고, 설명이 사용자 목적과 연결되며, 존재하지 않는 기능·출처를 주장하지 않는 것”으로 정의한다. Q-09·10은 별도의 필수 통과 항목이다.

## 8. 범위 외 사항(Out of Scope)

수업 자료가 요구하는 MVP 범위 합의를 위해, 다음 항목은 이번 초안의 필수 구현에서 제외한다.

- 회원가입·로그인, 사용자별 계정과 영구 대화 이력.
- 즐겨찾기, 별점·리뷰, 커뮤니티, 결제.
- 스킬 자동 설치·실행, 사용자 프로젝트의 코드 자동 수정, 원클릭 프로젝트 개발.
- GitHub 전체의 무제한 자동 수집·상시 크롤링.
- 독립 실행 에이전트·MCP 서버·일반 라이브러리까지 포괄하는 통합 추천.
- 추천 후보의 안전성·품질·모든 개발환경 호환성 보증.
- PDF·이미지·동영상·실행파일의 업로드 분석. 현재 시안에 있는 텍스트·코드 파일과 ZIP을 우선 지원한다.
- 모든 파일을 제한 없이 분석하거나 이전 대화 전체를 이해하는 기능.
- 운영자 전용 관리 화면, 다국어 서비스, 기업용 권한 관리.

‘원프롬프트 개발’은 **팀이 Skill Shelf 자체를 만드는 개발 방식**을 뜻한다. Skill Shelf 사용자의 프로젝트를 대신 개발하는 기능은 현재 제품 범위에 포함하지 않는다.

## 9. AI와 사용자의 역할

| 구분 | 맡는 일 |
| --- | --- |
| AI가 수행 | 프로젝트 설명·분석용 파일 내용을 해석하고, 등록된 후보 중 관련 스킬을 선정하며, 추천 이유를 작성한다. |
| 서비스가 확인 | 입력·파일 한도, 후보 존재 여부, 출처·링크 일치, 처리 상태, 추천 방식, 실패 안내를 확인한다. |
| 사용자가 확인 | 스킬 원문, 자신의 AI 코딩 도구와의 호환성, 사용·설치 조건과 라이선스, 프로젝트 적용 여부를 판단한다. |

추천 근거가 부족하면 보완 설명을 요청하고, 답할 수 없으면 결과가 없다고 알린다. 원문이 없거나 호환성이 확인되지 않았을 때 이를 확인된 사실처럼 표현하지 않는다.

## 11. 원프롬프트 개발에 전달할 기준

통합 개발 프롬프트에는 이 PRD와 HTML 시안을 함께 제공한다. Tech Spec이 준비되면 함께 전달한다.

> Skill Shelf MVP를 구현한다. 제품 범위와 완료 기준은 이 PRD를 따르고, 화면 구성은 Skill_Shelf_Preview.html을 기준으로 한다. 수업의 Streamlit 앱 구현·배포 조건을 따른다. 실제 AI 추천, 파일 내용 분석, GitHub 갱신을 구현하고, 데모·키워드·AI 모드를 실제 동작과 일치하게 표시한다. 준비된 후보 외의 스킬이나 링크를 생성하지 않는다. 문서에서 범위 외로 지정한 기능은 추가하지 않는다. 모델·비밀키·수집 대상 등 팀 결정이 필요한 항목은 Tech Spec의 확정값을 따른다. 각 P0 기능의 인수 조건으로 구현 결과를 확인하고, 검증하지 못한 항목은 분리해서 보고한다.

실제 모델·데이터 구조·함수/API·배포 설정·비용은 Tech Spec에 작성한다. 본 PRD만으로 기술 결정이나 미확정 사항이 모두 승인된 것으로 간주하지 않는다.
